# 5.25.1 — Advisory runtime compatibility

## Changes

- Pi 0.99.1 is the tested baseline. Older/future versions are unverified, not a delivery prohibition.
- The Pi launcher's Node.js 22.19 floor warns on stderr and attempts execution. Missing binaries/renders, failed probes/spawns, nonzero exits and signals keep their actual outcomes.
- Bedrock, Vertex, Foundry and custom API endpoint configuration produces advisory Claude channel diagnostics. MCP initialization remains independent; initialized channels attempt normal notification delivery.
- Scheduled notifications ignore version/provider labels as a prohibition. Occurrences and receipts retain structured warnings. Actual lifecycle, endpoint, initialization and wire/protocol failures still apply.

Compatibility warnings do not mean verified support, native receipt, consumption or task completion. No changes to global model profiles or defaults are included.

## Cutover and limits

From landed main, refresh the required CC render and generated plugin copy, update the installed plugin, and deliberately restart the dashboard. Loading new plugin files or `/reload-plugins` does not replace an already-running channel MCP process. Start/restart only the appropriate channel process; do not stop unrelated human sessions as cleanup.

Old processes can still return their old 503 refusal. Keep that runtime failure visible until they load the new code. Legacy unsupported labels alone neither prove initialization nor justify changing provider configuration.

Cancelled/ended schedules and historical policy-blocked records are not replayed or revived. After rollout, the lead recreates only his own monitoring reminder and verifies an emitted occurrence reaches the current Pi session and is acknowledged. Schedule admission or source tests alone do not prove restored reminders.

Builder verification uses isolated current/nonbaseline/legacy fixtures, normal outbox delivery, native-error negatives, and fresh MCP SDK channel processes from source and the rendered artifact. A notification received by the SDK test client is not evidence that a real Claude application/provider consumed it. Real provider/application consumption and the live Pi reminder receipt/ACK remain separate checks.
